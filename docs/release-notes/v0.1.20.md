## Compute 0.1.20: a Cloudflare Workers execution provider

Compute can now run **short-lived, request-driven WASI workloads on
Cloudflare Workers**, including on Cloudflare's free plan, through the same
provider boundary as local and remote providers. Compute stays the
authority. Admission, placement, receipts, and state are Compute's, and
Cloudflare holds only the Workers Compute deployed.

```sh
compute cloudflare profile                                   # what the free plan runs and refuses
compute cloudflare init --account-id <id> --output ~/.compute/cloudflare-pool.toml
read -rs CLOUDFLARE_API_TOKEN && export CLOUDFLARE_API_TOKEN
compute cloudflare validate --provider cloudflare
compute cloudflare deploy --provider cloudflare hello.wasm    # explicit, idempotent
compute run hello.wasm --provider cloudflare                  # placement, admission, receipt
compute cloudflare delete --provider cloudflare --module hello.wasm
```

Guide: [docs/cloudflare.md](https://github.com/rkendel1/compute/blob/v0.1.20/docs/cloudflare.md).

### What the free-tier profile (`workers-free`) is, and is not

- It runs **WASI command modules**, one invocation per request, with
  arguments, environment, stdin, stdout, stderr, and an exit code.
- A Worker is a V8 isolate. It is **not a Linux VM and not a container**.
  Process runtimes (Node, Python, …), native executables, shells, persistent
  processes, containers, files, outbound network, sessions, durable jobs,
  application deployments, and local inference are refused explicitly,
  before anything is sent to Cloudflare. Cloudflare Containers is a separate
  paid product and is not used.
- Cloudflare enforces **10 ms of CPU time per invocation, 100,000 requests a
  day, and 128 MiB of memory** on the free plan (as documented on
  2026-10-17). Exhausted quotas surface as `quota_exhausted` and CPU or memory
  limits as a `killed` execution. Compute never moves a workload to another
  provider.
- **This is not free general-purpose compute, and not unlimited.**
  Cloudflare may change its plans. You remain responsible for your
  Cloudflare account and its usage.

### Evidence stays honest

A deployment receipt proves only that Cloudflare accepted a Worker. Each
invocation has its own record, which says whether the answering Worker
reported the deployed workload. Executions return an `ExecutionResult` with
a `compute.receipt@1` bound to the placement, admission, provider identity,
and deployment. Execution never deploys implicitly, and retries never create
a second Worker. The API token never appears in configuration, receipts,
records, errors, or logs.

### Compatibility

- Additive contract changes: provider identity and pool kind `cloudflare`
  (`compute.cloudflare@1`), error kind `quota_exhausted`, and runtime source
  `provider`. Existing providers, pools, receipts, and certified platform
  support are unchanged. A pool without a Cloudflare member behaves exactly
  as before.
- **Compute Configured** declares the provider as optional in its profile,
  ships the example pool file and workload, and adds
  `compute-configured-cloudflare-setup`, which writes a credential-free pool
  file under `COMPUTE_HOME` and never overwrites an existing one.
  `compute-configured-verify` checks the provider's profile and capability
  reporting without credentials.
- Linux x86_64 stays Certified and macOS ARM64 stays Preview.

### Testing

Deterministic tests run against a local fake of the Cloudflare API and
workers.dev that executes the deployed modules. The JavaScript harness is
tested under Node against real WASI modules. A live smoke test (deploy,
invoke, verify evidence, delete) runs only with explicit Cloudflare
credentials. It fails rather than passing when asked to run without them.
