## Compute 0.1.21: stack-agent, hardened sessions, and a local API that is not open to everything

### compute-configured

- **The agent is stack-agent** ([rkendel1/stack-agent](https://github.com/rkendel1/stack-agent),
  pinned to `e73e74a`): Chip and FX in Rust. The npm Chip/Eve agent and npm
  FX are gone. `compute-configured-agent` starts it from an allow-listed
  environment; its service refuses non-loopback addresses and persists works
  under `COMPUTE_HOME`.
- **Projects load into environments with a computer**, and are listed there;
  `compute environment source` loads a Git source at an exact commit.
- Managed services run on the bundled Node from an empty environment; the
  profile and setup say what runs without an AuthBoundry authorizer.
- The profile checks third-party licenses, records a digest of the installed
  `node_modules`, and release assets carry signed build provenance.

### Sessions and computers

- `compute session exec --stdin --follow --output-bytes`, and `--env NAME`
  takes the value from your environment (never on a command line).
- `compute session file read|write|list`: workspace-relative only; a path
  that resolves outside the workspace, links included, is refused.
- Output is bounded (16 MiB per stream by default); truncation is a flag
  with the true byte count, not an error.
- Computers take `--host-profile` (restricted/isolated): commands write only
  their workspace and get a memory limit. Commands in a computer are admitted
  under its environment's policy.
- Job requests are sealed at rest (AES-256-GCM); a command's values are in
  no persisted request, status, or event file.

### Containers

- Session containers drop all capabilities but six, set no-new-privileges,
  a 4096-process limit, and an init; `--container-oci-runtime runsc`
  selects gVisor. Verified against a real Docker engine from inside the
  container, in CI.
- Container sessions with network `none` can be created and used (they were
  refused before).

### Evidence

- Targets sign every receipt (Ed25519); `compute receipt verify --signed-by`
  pins the key. Receipts record the session substrate (`compute.substrate@1`:
  container engine, or the VM's kernel and rootfs digests and limits).

### Workspaces and checkpoints

- Symbolic links are workspace content; hard links are read as files.
- Exports and seeds move in chunks; the bound is 256 MiB (was 8 MiB).
- An archive without its end-of-archive marker is refused (a cut on an
  entry boundary used to read as a smaller workspace).

### Local control plane

- `compute up` requires a token on every API request, kept owner-only in
  `$COMPUTE_HOME/daemon.token`. The CLI reads it; the address `compute up`
  prints (and opens) carries it in its fragment, which no server sees.
  **Open the address `compute up` prints**, not a bare `http://127.0.0.1:8787/`.

### New, and what is not claimed yet

- `compute egress serve`: an allowlisted, DNS-pinned egress gateway that
  refuses private addresses and domain fronting and adds credentials for
  chosen hosts (held only by the gateway). Credential custody is local.
- `compute serve --session-provider microvm` (Linux, KVM, Firecracker): a VM
  per session with its own kernel, no network interface, and egress only
  through the gateway. Boot, isolation, egress, and stdin are exercised on
  KVM in CI; **suspend with memory kept is not yet verified there**, and
  macOS has no VM provider.
- Not done: interactive terminals (PTY), streamed output beyond log polling,
  machine fork, and owner-scoped reads on the control plane (any operator
  with read scope sees every computer view).
